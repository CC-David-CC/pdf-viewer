# PDF Viewer lifecycle review

Based on cae648c69; no deployment. The concrete fix replaces large `Uint8Array.from` conversions in the PDF Viewer and Document PDF preview launcher with typed-array copies. PDF.js may transfer/detach the worker input, so the copy preserves ownership and avoids mutating the file mirror or Document's source buffer. **It is still a full additional buffer**, not zero-copy: a 104 MiB preview allocates at least another 104 MiB in each copying stage and copying remains synchronous on the UI thread. Closing a preview also zero-fills its retained source array synchronously in the desktop close path. A future explicit ownership/transferable or Blob/stream-based design should reduce copies only after cancellation, account isolation, source preservation and PDF.js behavior are verified. No such optimization is claimed here.

The existing PDF viewer cancels render/text tasks, invalidates stale loads, disconnects ResizeObserver, unsubscribes from files and destroys candidate/current PDF.js loading tasks on dispose. Its fit/zoom code caps canvas area. Existing workflow tests passed at desktop and emulated phone sizes for reading, text selection, search, navigation, resizing and failed-open recovery. The isolated desktop test `tests/pdf-lifecycle-browser-review.test.mjs` checks two My files documents at 4K, PDF worker cleanup, the actual Document Editor preview, a 104 MiB preview with preserved source-byte ownership, and account isolation. It deliberately rejects large `Uint8Array.from` usage in the tested path. This was a large in-memory preview, not a 104 MiB server-file transfer, and the preview uses substantial memory. Physical devices, maximum 128 MiB files, broad PDF format coverage and worst-case PDF rendering performance remain unqualified.

Run the review in an isolated two-app catalog with `tests/jsketcher-preview-csp.py --isolated`, a dedicated Chromium and loopback `CODI_TEST_URL`/`CODI_TEST_CDP`. `CODI_SKIP_LARGE=1` skips the 104 MiB portion for a lighter follow-up. The first cleanup assertion incorrectly assumed all workers on the page belonged to PDF.js; an unrelated guest worker remained. The test was corrected to identify PDF workers by their script URL. The corrected lighter follow-up passed the held-read close/cancellation path and exact PDF-worker assertion; it skipped repeating the 104 MiB portion.
